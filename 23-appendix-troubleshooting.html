Appendix B — Troubleshooting

Troubleshooting

A field guide to the failure modes a new student is likely to hit. Organized by symptom; each entry has the root cause and the fix.

B.1 Setup

B.1.1 conda env create errors out on parcels

Symptom: ResolvePackageNotFound: parcels=3.x or compiler errors during the build of parcels.

Root cause: parcels has C extensions that need a working compiler. On macOS, this means Xcode CLI tools; on Linux, gcc.

Fix: install build tools. On macOS: xcode-select --install. On Ubuntu: sudo apt-get install build-essential. Then retry conda env create -f environment.yml.

If still failing, try mamba (conda install -n base mamba; mamba env create -f environment.yml) — mamba’s solver is faster and more reliable.

B.1.2 cartopy import error about GEOS or PROJ

Symptom: OSError: Could not find/load shared object file: libgeos_c.so.1

Root cause: cartopy’s binary doesn’t match the conda-installed geos/proj versions.

Fix:

conda update -n driftscope cartopy proj geos

Or, more aggressive: conda remove cartopy && conda install -c conda-forge cartopy.

B.1.3 python -m driftscope.fetch opens a browser asking for login

Symptom: copernicusmarine.subset() halts and tries to open a browser window for OAuth login.

Root cause: COPERNICUSMARINE_USERNAME / _PASSWORD not in env.

Fix: edit .env, fill in your credentials. Run from the repo root so load_dotenv() finds it. Sanity check:

python -c "import os; print(os.environ.get('COPERNICUSMARINE_USERNAME'))"

B.2 Data fetch

B.2.1 CDS request hangs forever

Symptom: cds.retrieve(...) for ERA5 sits at “Queued” or “Running” for >5 minutes.

Root cause: Big requests on busy days take a while. Most BoB requests finish in 30–90 seconds.

Fix: be patient. If you’re really stuck, log into cds.climate.copernicus.eu and check your queue — sometimes the API key is rate-limited and the request didn’t even submit.

B.2.2 HYCOM fetch fails with HTTP 503 / 404

Symptom: HTTPError: 503 Service Unavailable from tds.hycom.org.

Root cause: The HYCOM THREDDS server has weekly maintenance windows (typically Thursdays 18:00 UTC) when OPeNDAP requests fail.

Fix: wait a few hours and retry. If persistent, switch to CMEMS for the day’s work — the rest of the pipeline is unchanged.

B.2.3 Drifter fetch returns empty CSV

Symptom: data/drifters/<region>_<dates>_drifters.csv has 4 lines (header + units + 0 rows).

Root cause: No GDP drifter active in the bbox/time. This is normal — drifters are sparse.

Fix: widen the bbox or shift the dates. The eastern BoB has the densest drifter coverage in the region; try (85, 8, 95, 16) for 2025-04 onward.

B.2.4 TPXO tide fetch errors with “TIDE_MODEL_DIR not set”

Symptom: RuntimeError: TIDE_MODEL_DIR not set in .env.

Root cause: Tides require a manual one-time setup (TPXO download).

Fix: register at tpxo.net, download TPXO9-atlas-v5 NetCDF, set TIDE_MODEL_DIR in .env to the unpacked directory. See Chapter 3.

B.2.5 pyTMD errors about “model not found”

Symptom: pyTMD.compute.tide_currents() raises FileNotFoundError: Model_TPXO9-atlas-v5_nc not found.

Root cause: One of the seven pyTMD 3.x quirks (Chapter 13). Most likely: TIDE_MODEL_DIR points at the model directory itself, but pyTMD wants its parent.

Fix: if your model is at ~/data/tpxo/TPXO9_atlas_v5/Model_h_M2_v5_nc, set TIDE_MODEL_DIR=~/data/tpxo/. pyTMD discovers the model from there.

B.3 Simulation

B.3.1 “All seed points landed on land/NaN”

Symptom: RuntimeError: All seed points landed on land/NaN.

Root cause: Your seed disk is too close to or on top of land (very common in delta regions).

Fix: move the seed offshore. For Sundarbans:

python -m driftscope.simulate \
    --seed-lon 89.0 --seed-lat 20.8 --seed-radius 0.3

…or use --seed-mode bbox to fill the entire ocean portion of the bbox uniformly.

B.3.2 Particles all delete by day 3

Symptom: 500 particles seeded, 50 alive at day 3, 0 alive at day 10.

Root cause: The bbox is too small. Particles drift out of the domain and DeleteOOB removes them.

Fix: refetch with a wider bbox (~1.5× the typical drift distance: peak speed × runtime).

B.3.3 Simulation is suspiciously fast

Symptom: pset.execute() takes <1 second; trajectory file has 0 particles.

Root cause: All seed points landed on land in a way that run_simulation() didn’t catch (rare, but possible if the currents file’s land mask differs from our heuristic).

Fix: open the currents file and inspect:

ds = xr.open_dataset("...")
print(ds.uo.isel(time=0).count())  # should be > 0

If 0, your bbox is entirely land — fix the bbox.

B.3.4 parcels prints where='out' warning

Symptom: pages of UserWarning: 'where' used without 'out' from parcels’ particledata.py.

Root cause: parcels v3 + numpy 2.x deprecation. Library bug, not yours.

Fix: already filtered in simulate.py:19. If you see it, the filter was edited or numpy was bumped — update parcels (conda update parcels) or restore the filter.

B.4 Plotting

B.4.1 Trajectory plot looks like a single line

Symptom: Plot shows what looks like one trajectory with 81 points, not 500 trajectories.

Root cause: Loading the wrong file, or only the first particle’s trajectory.

Fix: check the dataframe length:

df = traj_to_dataframe(ds)
print(df['traj'].nunique(), 'trajectories')
print(df['time'].nunique(), 'time steps')
print(len(df), 'rows')

500 × 81 should give 40,500 rows. If it gives 81, you’re loading wrong.

B.4.2 Map shows particles in wrong hemisphere

Symptom: trajectory plot shows points on the wrong continent.

Root cause: HYCOM uses 0..360 longitude convention internally and sometimes leaks through. Check if your particle longitudes are >180.

Fix: in the post-processing, normalize:

df['lon'] = ((df['lon'] + 180) % 360) - 180

The fetcher does this on save; user code that reads the trajectory zarr directly may need to redo it.

B.4.3 SST plot shows “300 K” colorbar

Symptom: temperature axis is in 280–310 K range.

Root cause: forgot to convert OSTIA from Kelvin to Celsius.

Fix: T_celsius = T_kelvin - 273.15 before plotting. The dynamics-snapshot script does this explicitly.

B.5 Quarto book

B.5.1 quarto render fails with “command not found”

Symptom: bash: quarto: command not found.

Root cause: Quarto CLI not installed.

Fix: install from quarto.org/docs/get-started. Single binary, no Python dependencies. Smoke test:

quarto check

B.5.2 Code chunks fail to execute on render

Symptom: quarto render docs/ errors out on a {python} chunk.

Root cause: Quarto can’t find the right Python. By default it uses the system Python, which doesn’t have xarray, parcels, etc.

Fix: configure Quarto to use the conda env. Either:

  • conda activate driftscope before running quarto render.

  • Or set QUARTO_PYTHON env var to the env’s python:

    export QUARTO_PYTHON=/path/to/miniconda/envs/driftscope/bin/python
quarto render docs/

B.5.3 Math symbols render as raw \dots

Symptom: Equations show \frac{d\mathbf{X}}{dt} instead of rendered math.

Root cause: KaTeX/MathJax not loading. Most likely your output is PDF and the LaTeX engine is missing.

Fix: for HTML output: ensure JavaScript is enabled in the browser; math should render via MathJax. For PDF: install LaTeX (tinytex is the easy option):

quarto install tinytex

B.6 Performance

B.6.1 Simulation runs out of memory

Symptom: Python killed by OOM, or “MemoryError” during pset.execute().

Root cause: Likely too many particles for the available RAM — each particle has a few-dozen-byte state, and trajectories are written to disk in chunks. 100k+ particles can be heavy.

Fix: reduce --particles. 500–2000 is the sweet spot for exploration; 10k+ is for production-grade ensembles.

B.6.2 Plots take forever to render

Symptom: df.plot() on the full trajectory dataframe sits.

Root cause: 40,000+ scatter points × matplotlib = slow.

Fix: subsample. df.sample(n=5000).plot(...) is plenty for visual inspection. For final plots, use 2D histogram (np.histogram2d → imshow) instead of scatter.

B.7 When in doubt

  1. Read the docstring of the function that’s misbehaving. Most gotchas are documented there.
  2. git log -p path/to/file.py | head -100 — recent changes often reveal why a workaround exists.
  3. Memory files in memory/ hold notes on past gotchas (especially the pyTMD ones).
  4. scripts/ contain working end-to-end examples for every non-trivial use case. If you can’t get something to work, see if there’s a script that does it.

A mature Lagrangian-modeling workflow is 30% physics, 30% data plumbing, 20% bbox/grid bookkeeping, 20% troubleshooting. The first 30% is what’s interesting; the rest is what makes the first 30% reliable.
